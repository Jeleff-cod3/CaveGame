# Proximity Voice Implementation Notes

This note records the current integration points for free proximity voice chat and the implementation path now present in the repo.

## Current Repo Facts

- `Packages/manifest.json` includes `com.endel.nativewebsocket` and Unity WebRTC `com.unity.webrtc` version `3.0.0`.
- `CaveGameApiClient.BuildWebSocketUrl()` already converts the HTTP backend URL to `ws://` or `wss://` and appends the auth token as `?token=...`.
- `CaveGameSocketClient` is a JSON text WebSocket wrapper with queued sending, message callbacks, open/close/error callbacks, and debug counters.
- `backend/config/asgi.py` routes WebSockets through `TokenAuthMiddlewareStack(URLRouter(websocket_urlpatterns))`.
- `backend/realtime/routing.py` exposes `ws/lobby/<int:lobby_id>/` and `ws/game/<int:lobby_id>/`.
- `/ws/game/<lobby_id>/` is the right existing channel for WebRTC signaling because `GameConsumer` already authenticates the user, checks lobby membership, checks that the lobby is started, joins the runtime room, stores the channel connection, sends room snapshots, and relays game-state events to other members.
- Django/Channels will handle auth, room membership, player positions, audibility snapshots, and WebRTC signaling.
- Unity WebRTC will handle actual microphone/audio media.
- Do not build a custom PCM-over-WebSocket voice system. The WebSocket should carry only signaling, room, heartbeat, and interest-state JSON.
- Backend player IDs are stable strings generated by `LobbyMember.player_id` as `player_<user_id>`.
- Unity uses the backend-provided `playerId` when present and falls back to `player_<currentUser.id>` through `GetLocalPlayerId()` and `BuildPlayerKey()`.
- `MultiplayerPrototype` currently creates multiplayer avatars at runtime with `GameObject.CreatePrimitive(PrimitiveType.Cube)`. It creates a local cube with `LocalCubeController` and remote cubes with `RemoteCubeController`.
- `Assets/Prefab_objects/Player.prefab` is a basic `Player` prefab with mesh, collider, rigidbody, and `PlayerControllerLoose`, but the multiplayer runtime path does not instantiate it for local or remote players.
- `MultiplayerPrototype.ResolveRuntimeSpawnAnchor()` searches for an active scene object named `Player`, disables it, and uses its position as the multiplayer spawn anchor.
- `MultiplayerPrototype.PreSpawnRemotePlayers()` creates remote runtime cubes from the `game_started` player list.
- `MultiplayerPrototype.ApplyRemoteState()` also creates a remote runtime cube if a `player_state` arrives for a player that was not pre-spawned.

## Current Unity Message Handling

- Lobby socket messages are handled by `MultiplayerPrototype.HandleLobbySocketMessage()`.
- Game socket messages are handled by `MultiplayerPrototype.HandleGameSocketMessage()`.
- `room_snapshot` is deserialized into `RoomSnapshotDto`; each `snapshot.players` entry is passed to `ApplyRemoteState()`, then mammoth state and health are applied.
- `player_state` is deserialized into `PlayerStateDto` and passed to `ApplyRemoteState()`.
- `player_left` is deserialized into `LobbyEventDto`, converted to a player key with `BuildPlayerKey()`, then removed with `RemoveRemotePlayer()`.
- `pong` is deserialized into `PongDto` and passed to `HandleGamePong()`, which updates game RTT and last-pong time.
- `heartbeat` updates `lastGameHeartbeatReceiveTime`.
- The client sends local `player_state` on the game socket at up to 30 Hz, plus `ping` and `heartbeat`.

## Added Message Types

- `webrtc_offer`: client-to-server-to-target peer SDP offer relay.
- `webrtc_answer`: client-to-server-to-target peer SDP answer relay.
- `webrtc_ice`: client-to-server-to-target peer ICE candidate relay.
- `voice_interest_snapshot`: server-to-client list of currently audible peers, with distance/gain metadata if useful.
- `voice_peer_left`: server-to-client cleanup signal for voice peer teardown when a player leaves or becomes unavailable.
- `voice_presence`: optional client/server message for mic availability, muted state, and voice readiness.

The server should treat `fromPlayerId` as derived from the authenticated room member, not as trusted client input. `targetPlayerId` must resolve to another member in the same started lobby.

## Unity-Side Classes Added

- `VoiceWebRtcBootstrap`: initializes the Unity WebRTC runtime path once and runs the WebRTC update coroutine.
- `LocalVoiceSource`: starts/stops microphone capture and exposes a Unity WebRTC `AudioStreamTrack`.
- `WebRtcVoicePeer`: owns one `RTCPeerConnection` for a remote player, creates offers/answers, handles ICE, adds the local audio track, receives remote tracks, and exposes connection state.
- `VoiceSignalingController`: subscribes to the existing game socket message flow, sends `webrtc_offer`, `webrtc_answer`, and `webrtc_ice`, and routes inbound signaling to the correct `WebRtcVoicePeer`.
- `RemoteVoiceSpeaker`: attaches an `AudioSource` to the runtime remote cube transform and plays the remote WebRTC audio track with 3D audio settings.
- `VoicePeerManager`: applies `voice_interest_snapshot` updates, starts or stops peer connections for audible players, applies server gain, and owns retry cleanup after ICE/WebRTC failures.

These classes should attach voice playback to runtime-created remote cubes unless multiplayer spawning is first refactored to instantiate a multiplayer-ready prefab.

## WebRTC Foundation Added

- `Packages/manifest.json` now includes `com.unity.webrtc` version `3.0.0`, while keeping the existing `com.endel.nativewebsocket` dependency intact.
- `Assets/Scripts/Voice/VoiceChatConfig.cs` stores the first voice tuning values: `voiceEnabled`, `minVoiceDistance`, `maxVoiceDistance`, `voiceKeepAliveDistance`, `stunServer`, and `debugLogging`.
- `Assets/Scripts/Voice/VoiceWebRtcBootstrap.cs` can be placed in a scene, but `VoicePeerManager` also auto-creates it through `VoiceWebRtcBootstrap.EnsureExists()` before microphone capture or peer creation.
- `VoiceWebRtcBootstrap` keeps one instance alive with `DontDestroyOnLoad()`, rejects duplicate instances with a static guard, configures Unity WebRTC native logging, and starts `StartCoroutine(WebRTC.Update())`.
- Unity WebRTC 3.x no longer exposes the old explicit `WebRTC.Initialize()` and `WebRTC.Dispose()` methods. For this package line, the bootstrap work is starting the package update coroutine before media objects create tracks or peer connections.
- On application quit or owned-instance destruction, the bootstrap stops its update coroutine and resets its static guard.

## Backend Signaling Foundation Added

- `/ws/game/<lobby_id>/` now has backend primitives for targeted WebRTC signaling relay: `webrtc_offer`, `webrtc_answer`, and `webrtc_ice`.
- The backend validates flat signaling messages, derives `fromPlayerId` from authenticated game socket membership, and never trusts client-supplied sender identity.
- `VoiceRoomRuntimeState` tracks voice-capable players by lobby, channel, last-known position, audibility sets, and disconnect cleanup.
- `player_state` remains the movement transport and now also feeds server-side voice position state for audibility snapshots.
- `voice_interest_snapshot` is emitted from the game socket on a simple cadence so the 30 Hz movement stream does not produce excessive voice-interest messages.
- `ENABLE_WS_ORIGIN_VALIDATION=true` wraps the ASGI websocket app with `AllowedHostsOriginValidator`; it is off by default to avoid breaking local Unity clients that may not send browser-style origin headers.

## Unity Signaling DTOs Added

- `Assets/Scripts/Voice/VoiceDtos.cs` defines flat `JsonUtility` DTOs for `voice_interest_snapshot`, `webrtc_offer`, `webrtc_answer`, `webrtc_ice`, `voice_peer_left`, and `voice_presence`.
- `Assets/Scripts/Voice/VoiceSignalingController.cs` uses the existing game socket send path for outbound voice signaling and exposes callbacks consumed by `VoicePeerManager` and `WebRtcVoicePeer`.
- `MultiplayerPrototype` creates the signaling controller only after the game socket opens and the local backend `playerId` is known.
- Incoming game socket messages not handled by existing gameplay code are passed to the signaling controller, which only consumes known voice message types.

## Unity WebRTC Media Layer Added

- `Assets/Scripts/Voice/LocalVoiceSource.cs` captures the default Unity microphone, feeds it through an `AudioSource`, and exposes an `AudioStreamTrack` with WebRTC loopback disabled.
- `Assets/Scripts/Voice/WebRtcVoicePeer.cs` owns one `RTCPeerConnection` for one remote player, configures STUN from `VoiceChatConfig`, exchanges offer/answer/ICE through `VoiceSignalingController`, and attaches incoming audio tracks.
- `Assets/Scripts/Voice/RemoteVoiceSpeaker.cs` creates a spatial `AudioSource` child under the runtime remote avatar and applies gain/mute from `voice_interest_snapshot`.
- `Assets/Scripts/Voice/VoicePeerManager.cs` starts local capture once, creates peers for audible remote players, uses lexicographic `playerId` ordering for deterministic offer ownership, and disposes peers when players leave or disappear from the interest snapshot.
- `MultiplayerPrototype` remains a thin integration point: it creates the voice manager after the game socket opens, supplies runtime remote cube transforms, refreshes voice transform lookup when remote cubes spawn, and disposes voice peers when remote cubes or sockets are removed.
- The Unity side now creates peer connections and microphone capture, but it still relies on Django/Channels for signaling and audibility snapshots. It does not implement custom PCM-over-WebSocket audio.

## Proximity Stability Added

- Server `voice_interest_snapshot` messages are the source of truth for which remote peers should exist on the Unity client.
- The backend keeps audible peers alive through the configured hysteresis band: peers can start inside `max_voice_distance` and stay listed until they pass `keep_alive_distance`.
- The backend sends voice-interest snapshots on a low cadence, currently `0.2` seconds, so high-rate movement messages do not produce high-rate voice control traffic.
- Unity applies server gain from `voice_interest_snapshot` and also keeps the remote `AudioSource` in 3D linear falloff mode.
- Unity hard-mutes a peer locally if the reported distance is beyond `VoiceChatConfig.maxVoiceDistance`, while still allowing the peer connection to stay alive inside the server hysteresis band.
- `WebRtcVoicePeer` reports failed ICE or WebRTC setup errors back to `VoicePeerManager`; the manager disposes that peer and allows renegotiation after `VoiceChatConfig.peerReconnectDelaySeconds`.
- WebSocket reconnect or close disposes the current `VoicePeerManager`, local voice source, peer connections, and remote speakers. A new game socket creates a fresh signaling/peer manager.
- Missing microphone devices and WebRTC exceptions are logged as voice-only failures; the multiplayer session should continue running.
- `VoiceChatConfig.debugLogging` gates detailed voice logs for snapshots, peer creation, offer/answer/ICE flow, ICE state changes, remote track attachment, peer disposal, and mic start/stop.
- Pressing the existing multiplayer debug snapshot key includes a compact voice status block with microphone, active peer count, snapshot age, ICE state, and remote-audio status.

## Backend-Side Classes And Functions Added

- Message constants in `message_types.py` for the new voice messages.
- `is_valid_webrtc_offer(data)`, `is_valid_webrtc_answer(data)`, `is_valid_webrtc_ice(data)`, and related helpers in `validators.py`.
- `VoicePeerRuntimeState` to track player ID, user ID, last-known position, channel name, voice readiness, muted state, and last-seen time.
- `VoiceAudibilitySnapshot` or a simple payload builder for per-recipient audible peers.
- `update_voice_position_from_player_state(room, player)` to reuse the existing `player_state` flow as the source of proximity data.
- `compute_audible_peers(room, listener_player_id)` with a maximum radius and hysteresis band.
- `handle_webrtc_offer()`, `handle_webrtc_answer()`, and `handle_webrtc_ice()` on `GameConsumer`.
- `send_voice_interest_snapshot()` on `GameConsumer`, or a room-level cadence helper that sends snapshots at a lower rate than transform updates.
- Cleanup logic on `GameConsumer.disconnect()` to clear voice state and notify peers with `voice_peer_left`.

## Manual Test Scene Recommendation

Use the existing multiplayer flow first, preferably `Assets/Scenes/multiplayer_and_chunkmap.unity` for an end-to-end game test and `Assets/Scenes/multiplayerlobbytesting.unity` for a smaller lobby/socket smoke test if needed. Run two clients, create guest users, join the same lobby, mark ready, start the game, confirm both clients connect to `/ws/game/<lobby_id>/`, then verify signaling, ICE connection state, remote audio attachment to the runtime remote cube, player-left cleanup, and distance-based audibility changes.

## Risks And Assumptions

- Unity WebRTC package compatibility with Unity `6000.4.6f1` still needs Editor verification after Unity can reopen the project without another instance holding the project lock.
- STUN may be enough for local or simple network tests, but real Internet play may require TURN.
- `MultiplayerPrototype.cs` is already large, so voice logic should live in separate classes and only use small integration hooks in the prototype.
- The current backend room state is in memory. Redis/Channels handles cross-process messaging, but any voice runtime state stored only in process memory needs care if multiple Daphne workers are used.
- Audibility should not be recomputed for every 30 Hz transform message for every player. Store latest positions and emit interest snapshots on a lower cadence or movement threshold.
- Current remote avatars are runtime cubes, so adding voice only to `Player.prefab` would not affect multiplayer remote players.
- Existing token query-string auth is already used by Unity sockets. It is acceptable for the current prototype, but production hardening should use `wss://`, origin validation, strict lobby membership checks, and server-derived `fromPlayerId`.
